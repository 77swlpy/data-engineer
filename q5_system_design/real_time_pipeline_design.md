# Q5.1 - 实时数据管道设计

## 📋 题目背景

Olist 当前的数据是离线 CSV 导出。现在业务需求是——卖家希望**实时**看到自己的订单情况、买家评价、物流异常。

请设计一个**实时数据架构**，满足：

- 订单状态变更后 **30 秒内** 反映在卖家后台
- 评价文本进来后 **1 分钟内** 触发情感分析 + LLM 抽取
- 物流异常（如某订单延迟超过预计时间）**自动报警**到卖家
- 历史数据查询（卖家想看过去 6 个月的成交曲线）**毫秒级响应**
- 当前数据规模：**10 万订单/天**，预计 2 年内增长到 **100 万订单/天**

要求：800-1500 字 + 一张架构图

---

## 1. 整体架构图

> 用 ASCII art、Mermaid 或附图均可

CSV 仅作历史回填，实时需接入业务写入。假设允许简单评价走规则或小模型，需要 LLM 的评价须在入库后 60 秒内发起请求。

```text
订单服务 / 评价服务 / 物流回调
              │ 同一事务更新业务记录、写事件
              ▼
       MySQL 业务库（OLTP）+ Outbox
              │ 每2秒投递，收到确认后标记
              ▼
     托管 RabbitMQ（持久化、独立队列、重试）
       ├→订单队列→消费者→去重、更新快照与日汇总→MySQL 查询库
       ├→评价队列→消费者→规则/小模型、按需LLM→MySQL 查询库
       └→物流队列→消费者→到期任务→每30秒检查→通知卖家

MySQL 查询库 → Redis 热点缓存 → 卖家API → 后台页面（每5秒刷新）
                 状态5秒/曲线30秒

消费者：保留基础容量 → 积压时扩容 → 低谷缩容
历史CSV → 校验、核对增量边界 → 查询库回填
已投递Outbox事件、原始文件 → 对象存储归档
```

业务更新与 Outbox 同事务提交，事件携带唯一 ID 和业务版本，持久化队列配合发布确认支持失败重试。订单链路预算为采集 2 秒、投递处理 10 秒、缓存过期 5 秒、页面轮询 5 秒，共 22 秒，预留 8 秒。评价独立消费，避免模型阻塞订单。物流每 30 秒扫描到期任务，发现没有新事件的超时，核实状态后通知卖家。

## 2. 数据存储选型

> 哪些数据进 OLTP、哪些进 OLAP、哪些进消息队列、哪些进缓存？为什么？

MySQL 业务库承担 OLTP，保存订单、明细、原始评价、物流及通知记录；独立查询库存最新快照、抽取结果与卖家日汇总，隔离交易负载。按卖家、日期建立索引，六个月曲线只查约 180 行，目标为缓存未命中时 API 的 P95≤200 毫秒；接口按登录卖家鉴权，缓存键包含卖家 ID。

成交额按下单日归属，仅计已送达订单中该卖家的商品价与运费。消息队列用于削峰、重试；Redis 缓存热点，订单 TTL 为 5 秒、曲线为 30 秒，假设曲线允许分钟级新鲜度；对象存储保存原始文件与归档事件。

## 3. LLM 部分如何避免成本失控

> 100 万订单/天，如果每条评价都过 LLM，年成本估算多少？怎么优化？

按 2026-11-27 核对的 GPT-6 Luna 标准价，输入／输出分别为 $0.10／$0.50 每百万 tokens。假设平均 800 输入、300 计费输出 tokens（含推理），单次成本为：

`(800×0.10＋300×0.50)÷1,000,000＝$0.00023`

每天百万条评价全部调用，全年 365 天为 **$83,950**。[官方价格](https://developers.openai.com/api/docs/models/gpt-6-luna)

本地文本评价／订单为 40,950／99,441，折算约 **$34,571/年**。假设 20% 需 LLM、结果缓存命中 20%，再留 10% 费用余量，约 **$6,084/年**；十万单约 $608。这些比例与 token 用量待验证，模型更换后须重算；不含基础设施费用。

简单文本由规则处理，复杂或评分矛盾的文本送 LLM。用葡语样本比较**准确率、P95 时延和每条合格结果成本**，选择达标且费用最低的模型；按完整输入及模型版本缓存，精简提示和 JSON 输出，限制异常重试。

日预算只告警，超额继续正常调用，不承诺支出硬上限。Batch 的 24 小时窗口仅用于历史补算，不承担在线一分钟要求。[Batch 说明](https://developers.openai.com/api/docs/guides/batch)

## 4. 三个最大的风险点和应对方式

### 风险 1：

**说明**：重复、乱序或丢失事件会导致状态倒退、成交额重复或漏算。

**应对**：监控 Outbox 积压并对账；按事件 ID 去重、业务版本防倒退，去重记录、版本更新及新旧贡献调整同事务提交，再确认消息。有限重试后入死信队列，修复重放；快照回填明确增量边界。[确认机制](https://www.rabbitmq.com/docs/reliability)

### 风险 2：

**说明**：队列积压会超时，物流回传滞后或日期口径错误会造成误报。

**应对**：按端到端耗时扩容，故障时显示最后更新时间，恢复后补消费。预计日期按业务时区当日结束判超时；物流回传滞后时标“待核实”，通知持久化、幂等重试。缓存失效则限流回查。

### 风险 3：

**说明**：模型可能编造问题、错归责，异常调用和重试会推高费用。

**应对**：校验 JSON 和原文证据，抽查被分流评价；限流或故障时有限重试，先展示临时结果再补算，并记录超时。历史评价按订单与评价组合键关联；多卖家订单标“责任未确定”，不得让模型猜测。

## 5. 关于业务规模变化的考虑

> 10 万订单/天 vs 100 万订单/天，架构会有什么不同？

百万订单/天平均 11.6 单/秒；按每单 10 个事件、10 倍峰值估算，约 1160 个事件/秒，以普通消费者作为起点，容量仍需压测。

十万单阶段暂缓专用 OLAP，保留基础消费者，按最老消息等待时间提前扩容、低谷缩容，并发匹配 API 配额。百万单阶段也先压测；多维历史扫描成为瓶颈再引入 ClickHouse，保存历史事实与版本化汇总；需要长期回放再迁 Kafka。迁移须回填、双跑核对。

验收覆盖峰值、冷缓存、扩缩容、重复乱序、消费后崩溃、物流超时和 LLM 限流，同时记录延迟、错漏率与单位成本；时效均为待验证目标。
